## 修掉的隐藏 Bug：连续天数在非 UTC 时区恒为 0

- 现象：`getActiveDays` 用 `(startAt / 86400000) * 86400000` 分桶，这是 **UTC** 口径；而 `calcStreak` 用 `DateUtils.startOfDay`（本地 0 点）比对。东八区下前者得到的是当天 08:00（或前一天），永远匹配不上 → 连续天数显示为 0。
- 第一版修法用 `strftime('%s', startAt/1000, 'unixepoch', 'localtime', 'start of day')` —— **仍然是错的**：SQLite 的 `%s` 不会补偿时区偏移，返回的是「本地日期串按 UTC 解析」的时间戳，实测东八区偏差 8 小时（用 Python sqlite3 在 Windows 上按固定 epoch 验证才看出来）。
- 最终方案：SQL 只产出 `date(...,'unixepoch','localtime')` 的 **日期串**（实测分组正确），时间戳换算交给 Kotlin 的 `DayKeys.parse`。
- 教训：**SQLite 里做时区相关的日期分桶，`strftime('%s')` 不可信；让 SQL 出日期串、让应用层（java.time）出时间戳**。另外 Windows 上 `time.tzset()` 无效，验证时区逻辑必须用固定 epoch 而非 `os.environ['TZ']`。
- 顺带把 `weekDaily` 的逐日循环从 `+ DAY_MILLIS` 改为 `DateUtils.addDays`，避免夏令时偏差。
