## v1.1.40 —— 落后标签下按钮错位 / 高卡内容偏少 / 缩放松手抖动

**用户反馈（附手机截图）**：「当存在落后几天的标签时，下面的开始按钮位置就有问题了，我不要求你兼容超小屏，兼容1080p、1.5k、2k即可；1x2、1x3、1x4的卡片上内容还是有点少了；当我拖动一个卡片调整大小时，松手的瞬间，其它卡片大小也会一抖」。

**改动**：
1. **按钮错位**：根因是 `PlanFace` 把 `Spacer(weight)` 放在头部与数值区之间，数值区+进度条+按钮全压在卡片下沿；多一个「落后 N 天」chip 和周期行就把这一坨挤出可视区。改成高卡（`stacked = !dense && h>=150dp`）上下各一段等权 `Spacer(weight)`：信息落中段、按钮由撑杆稳定贴底；`TimerBar` 再收 6dp end padding，与右下角白色角标分开。节奏 chip 与周期信息**合并成同一行**，不再各占一行。
2. **高卡内容**：新增 `rangeText`（`M/d–M/d · 第 N/M 天`）、`每日目标 X 分 · 距结束还有 N 天`、以及一条**计划周期进度条**（`cyclePercent = dayIndex/totalDays`，用 startDate/endDate/today 现算，不查库），`showExtra` 只在 `h>=230dp` 的 1×3/1×4 类高卡出现。三行信息各司其职，不重复天数。周期信息阈值从 `h>=150` 放宽到 `h>=130`，1×2 也有。
3. **松手抖动**：渲染循环里 `faceCols/faceRows` 改为**只有 active 卡跟 `shown`（pushed/pending/box）走，其余卡一律用 `box`（packed = DB 权威规格）**。松手瞬间 shown 的数据源会切换，任意一帧规格不一致就会让整排卡的 `animateDpAsState` 弹簧抖一下；`arrange` 本来不改尺寸，所以锁死安全。计划卡和行程卡两处循环都改了。
4. 兼容目标按用户要求定为 1080p / 1.5K / 2K，保留 `dense` 降级但不再为超小屏削减中等以上规格的信息密度。

**踩坑**：`cyclePercent` 一开始写在 `totalDays`/`dayIndex` 定义之前，Kotlin 编译报 Unresolved reference，把声明顺序理顺即可。

**环境踩坑（重要）**：MuMu 这轮 adb 极不稳定——`127.0.0.1:16384` 拒绝连接；`adb kill-server && start-server` 后设备变成 `emulator-5554`，且在 offline/device 之间抖动；`adb install` / `pm install` 常因掉线失败。可靠做法：**同一次 shell 调用里** `adb start-server → adb connect 127.0.0.1:5555 → adb -s 127.0.0.1:5555 install/shell/exec-out`，不要跨调用保持连接。`push` 到 `/data/local/tmp` 再 `pm install` 可作备选。MuMu 实装在 `D:/android/MuMu Player 12`（不是 Program Files 那个空目录）。

**MuMu 实测**：新包安装后（1272×2261 / density 240），有「落后 5 天」的 1×2 / 1×3 / 2×1 / 3×1 卡按钮都完整、离下沿有间距、不与白色角标重叠；1×3 卡出现周期进度条与附加信息，中段不再空。临时把 Plan 改成 1×3 验证超高规格，再拖动 Stretch 从 1×1 缩放到 2×2，抓松手前 + 松手后 3 帧，用像素 bbox 比对其它卡（Run / Write）宽度**四帧完全一致**，抖动消失。**测试改动已全部还原**：Plan 回 2×2@(0,5)、Stretch 回 1×1@(2,3)、Review 回 (0,4)、Auto 回 (3,4)，重启确认 8 张卡布局正常。713 条单测全绿。

**遗留**：前几轮测试残留 `plan_logs` 两条（plan 5，403s@11/7 与 600s@11/8）仍在，未擅自改数，已多次告知。

## v1.1.41 —— 首次拖动/缩放时其它卡「缩放抖一下」根因与修复

**用户反馈**：「每一个卡片首次调整位置或调整大小松手时，其它卡片都会抖动缩放一下」。上一轮只锁了「非活动卡尺寸用 box」，没根治。

**定位过程**：
- 加临时 `LaunchedEffect` 日志打印每张卡的 w/h 与格坐标，确认**尺寸 target 全程不变**，抖动不是 `animateDpAsState` 引起。
- 但直接读 DB 发现：一次位置拖动后 Review 从 **3×1 变成 2×1**、Auto 从 **1×1 变成 2×1**——其它卡是**规格真的被改了并写进库**，所以会「缩放」；写回后 DB 稳定，故只在「首次」发生。
- 排除 `CardBoard.normalize`（只夹 1..4）和 `arrange`（`return cards.map { placed[...] }` 保持输入顺序、不改规格）。

**三处根因与修复（DayCardBoard.kt）**：
1. `planBoxes = packed.take(plans.size)` / `tripBoxes = packed.drop(...)` 按索引切，只要 plans/trips 顺序或数量有一帧和 packed 对不齐就会取到别人的 box → 改成 `packed.associateBy { "p${id}"/"t${id}" }` 后按 id `mapNotNull` 对号入座。
2. `settle` 里 `commitOne(arranged[it], ...)` 把 `arranged` 的 cols/rows 写给**所有 changed 卡**。改成：非锚点卡用 `base` 里同 id 卡的规格 `moved.copy(cols=original.cols, rows=original.rows)` 覆盖，**邻居只改位置、绝不改规格**，只有锚点允许改尺寸。
3. `rememberCardOffset` 原来 `if (active || !gestureRunning) return target` 提前返回，`animateIntOffsetAsState` 节点在松手那一帧被销毁、返回值从动画中间值瞬切到 target。改成动画 State **常驻**，`return if (active) target else animated`，并删掉不再需要的 `gestureRunning` 参数。

**MuMu 实测**（1272×2261 / density 240，设备 127.0.0.1:5555）：
- 先 SQL 完整还原 8 张卡布局与规格；冷启动进页面后查 DB，规格一个没变（排除 `autoPlaced` 启动写回的嫌疑）。
- **首次拖动** Read：只有 Read (2,0)→(1,0)、Code 被挤到 (2,0)，8 张卡的 `cardCols/cardRows` **全部不变** ✓。
- **首次缩放** Stretch 1×1→2×2：只有 Stretch 规格变，Review 仍 3×1、Auto 仍 1×1、Run 仍 2×1；抓松手前 + 松手后 3 帧，像素 bbox 比对 Write 卡尺寸四帧**完全一致**（296×606）✓。
- 测试布局已再次完整还原（含规格），713 条单测全绿。临时诊断日志已删除。

**教训**：这类「只在第一次发生」的 UI 抖动，优先查**有没有把错误的规格写进持久化数据**——纯视觉层加锁治标不治本。诊断时直接前后 diff 数据库比截图更快命中。
