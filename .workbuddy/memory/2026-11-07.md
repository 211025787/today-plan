## ⏱ 开屏文字真正的 0.3 秒在「首帧之前」（v1.1.18）

用户：「卡屏文字动画可以再提前 0.3 秒播放，播放速度不变」。

- **先确认一件事**：v1.1.17 已经把 `brandAlpha` 前面的 `delay` 全部删掉了，`animateTo` 就是 `LaunchedEffect` 里的第一件事——时间轴上**没有可以再往前挪的东西**。用户看到的 0.3 秒不是动画晚开始，而是**开屏首帧本身就晚了 0.3 秒**：系统启动帧那枚图标一直挂在屏幕上，我们自己的第一帧还没画出来，所以"图标在、字不在"的空档被读成"文字动画晚播"。
- **为什么不能靠"把动画往前拽 300ms"解决**：真要拽，就得让动画在第一帧之前就开始计时（拿 `System.nanoTime()` 做锚点）。但 `LinearOutSlowInEasing` 前 300ms 就走到 α≈0.58，第一帧一出来文字就是半透明的，等于把淡入砍掉——用户明确说了"播放速度不变"，这么干会被读成"文字一下子跳出来"。**结论：可见 alpha 在第一帧必须≈0，所以"文字更早" ≡ "首帧更早"，只能从启动链路上抠时间。**
- 改动（都不碰动画参数）：
  - `MainActivity.onCreate`：`requestHighestRefreshRate()`（改 `window.attributes`，会触发窗口重排）和 `requestNotificationPermissionIfNeeded()`（起系统弹窗）从 `setContent` 之前挪到 **`window.decorView.post {}`**；权限弹窗更晚一步，挂到 `WarmSplash.onFinished` 里——系统弹窗会压住动画的帧，盖在手写上一定掉帧；
  - `FocusListApp.onCreate`：`Notifier.ensureChannels()`（几次跨进程调用）+ `ChimePlayer.preload()`（要打开 5 个 wav，约 1MB）挪进 `appScope.launch`，不再和首帧抢主线程；
  - `WarmSplash`：淡入改成 `LaunchedEffect` 里的**第一句话**，`launch` 只包名言那条线（`delay(1300)` → 手写 → 回调 → `delay(650)`）。少一次协程分发 = 少等一帧。
- 时间轴本身一个字没改：0~1200ms 淡入（`tween(1200, LinearOutSlowInEasing)`）、1300ms 落笔、写完回调组合主界面、+650ms 淡出。
- **经验**：以后遇到"某段动画晚了 X 毫秒"，先分清是**动画晚开始**还是**首帧晚出现**。前者改 `delay`/时间轴，后者只能砍首帧前的主线程重活（窗口属性、权限、SoundPool、通知渠道、字体/数据加载）。这一版属于后者，也是这条线最后一处可优化的地方——再往下就只剩 debug 包本身的启动开销了。
- 包 1.1.18（code 238），691 测试全绿。

## 🩹 开屏点一下变纯色（v1.1.19）

用户：「在『暖厉』动画页时，点击屏幕会变成纯色画面」。

- 原因很直接：v1.1.17 把主界面组合改由 `onQuoteWritten` 触发，于是**跳过路径**里 `warmUpApp` 一直是 `false`。点一下 → `onFinished` → `splashVisible = false` → 开屏用 280ms 淡出，而底下**一片空白**，露出来的就是窗口底色（那屏纯色），而且永远不会恢复——主界面根本没被组合过。
- 改法（`MainActivity`）：
  - 退出统一收口成 `exitRequested` 一个状态，`LaunchedEffect(exitRequested)` 里判断：主界面还没组合就先 `warmUpApp = true`，`withFrameNanos` 等**两帧**（等 `AppScaffold` 组合 + 绘制）再把 `splashVisible = false`；
  - 正常播完时 `warmUpApp` 早已是 true，直接淡出，行为不变；
  - 单状态天然幂等：连点两下不会把还盖着的开屏摘掉；
  - 顺手给权限申请加了 `notificationPermissionAsked` 闸门——跳过和播完都可能触发，重复 `launch` 会顶掉正在显示的系统弹窗。
- **经验**：任何「提前把某层藏起来」的优化，都要检查**所有**能让它提前藏起来的路径。这里 `onFinished` 有两条来源（自然播完 / 轻点跳过），只有自然播完那条满足「底下已经组合好」的前提。以后凡是把「组合/加载」从时间轴上挪走，就得给「用户手动快进」的路径补一条等待。

## ⏩ 开屏去掉点击跳过 + 文字再提前 0.3 秒（v1.1.20）

用户：「1. 不对，这个画面不应该支持点击，要正常把文字播放完；2. 文字播放再提前 0.3 秒」。

- **去掉点击跳过**：`WarmSplash` 整屏不再挂 `pointerInput`/`detectTapGestures`，`skipped` 状态、
  由此产生的 `LaunchedEffect(quote, skipped)` 双 key、`MainActivity` 里那套
  `exitRequested` + `withFrameNanos` 等待逻辑全部删除（跳过路径没了，等待也没意义了）。
  上一版为了修「点一下变纯色」加的那套机器一起清掉，代码回到单一路径。
- **提前 0.3 秒，这次是真的动时间轴**：既然首帧之前的重活已经在上两版挪空，
  剩下的就只能承认——**首帧本身就是晚 300ms 的**。做法：
  - `MainActivity.onCreate` 里 `val splashStartNanos = System.nanoTime()` 打点，传进 `WarmSplash`；
  - `WarmSplash` 算出 `headStartMs = (now - startAtNanos)/1e6`，**截到 300ms 上限**，`offset = headStartMs/1200`；
  - `brandAlpha.snapTo(LinearOutSlowInEasing.transform(offset))` 先跳到曲线上对应位置，
    再用 `tween(remainMs, easing = ShiftedEasing(...))` 把剩下 900ms 播完；
  - 名言那行从 `delay(1300)` 改成 `delay(remainMs + 100)`，永远只隔文字收尾 100ms。
- **`ShiftedEasing` 的关键细节**：`tween` 的 easing 作用在**值的增量**（start→1）上，不是绝对进度上。
  所以直接 `base.transform(offset + f*(1-offset))` 会越播越快；必须按起始值归一化
  `(base(u) - base(offset)) / (1 - base(offset))`，才能得到 `value(f) = base(offset + f·(1-offset))`，
  也就是「每毫秒 alpha 变化量与原动画完全一致」。为此新增 `ui/splash/ShiftedEasingTest`（5 条，含逐毫秒差分比对），测试总数 691 → **696**。
- **代价要写清楚**：offset=0.25 时第一帧文字已是 ~58% 不透明。这是「把开头 300ms 挪到首帧之前」的必然结果——
  屏幕从系统帧切过来的那一瞬整屏都在换，所以看着不像跳变；但如果觉得"一出来就太浓"，
  只改 `MAX_HEAD_START_MS`（比如 150L）就能折中，曲线不用动。
- **经验**：用户说「提前 X 秒」时，如果时间轴上已经没有可挪的 delay，就说明剩余延迟在**首帧之前**。
  这时要么继续砍首帧工作量（有下限），要么把时间轴锚点前移到 Activity 创建那一刻、把看不见的那段扣掉。
  后者是唯一精确可控的做法，前提是缓动要能"从中间续播"。
- 包 1.1.20（code 240），696 测试全绿。

## 🃏 卡片拖动/缩放改成「永不重叠」（v1.1.23）

用户：「计划卡片页的拖动交互有时不准，点击指定卡片右下角却缩放了其它卡片；而且目前卡片拖动时会有堆叠的情况」。

- **两个现象其实同一个根**：
  1. `endResize` 走的是 `resizeToAllowed`，它**只钳制边界、完全不检查重叠**，所以一次缩放就能把卡盖到邻居身上，并直接落库；
  2. 一旦叠在一起，上层卡的 `ResizeGrip`（**56dp** 热区）就压在邻居右下角上，Compose 命中最上层 ——
     于是"点这张卡的右下角，缩放的却是那张卡"。加上卡片是按 `forEach { }` 输出、**没有 `key()`**，
     每次落库 `cardZ` 变化都会改变顺序，Compose 按位置复用节点，手势节点可能挂到别的卡上。
- **改法**：
  - `CardBoard` 新增三个纯函数：`maxFitCols` / `maxFitRows`（当前行/列不变时最多能长到几格）、
    `fitShapeAt`（按与期望值的距离排序，挑第一个放得下的规格；一个都放不下就保持原样，宁可不变也不叠）；
  - 拖动改成**按格吸附**：`moveBy` 只接受 `fitsAt` 通过的落点，手指划过别人的卡时落点停在上一格，
    整个拖动过程都不会叠；松手直接落库，不再需要 `resolveMove` 的"事后补救"；
  - 缩放实时上限改成 `maxFitCols/maxFitRows`，即"到邻居为止"，松手用 `fitShapeAt` 再验一次；
  - 每张卡包 `key(卡片 id)`；缩放手柄热区 56dp → **40dp**；
  - 老数据修复：进页面时按顺序"落位"，后到的卡若压到前面的卡就 `resolveMove` 到最近空位并落库（`autoPlaced` 去重）；
  - **乐观更新**：`commit` 时记一条 `pending = key to box`，渲染优先用它，等 `packed` 里出现同样坐标再撤。
    否则 Room 写库 → Flow 重新发射之间有一小段空窗，卡片会先弹回原位再跳过去，看着就像"拖了没放对"。
- 测试：`CardBoardTest` 22 → **30 条**（新增 8 条覆盖三个新函数的边界：邻居相邻/隔一格、右边界、limit、
  放不下保持原样、绝不越界），总数 696 → **704**，全绿。
- **经验**：这类"拖动不准"的 bug，先分清是**命中问题**（重叠/热区/组合身份）还是**数据问题**（落点没校验）。
  这次两者叠在一起：数据层允许重叠 → 视觉重叠 → 热区命中错卡。修数据层的重叠，命中问题也就跟着消失了。
- 包 1.1.23（code 244），704 测试全绿。

## 19:46 v1.1.25 修「缩放时邻居不实时让位」+ 挖出真正的重叠根因

用户截图反馈「还是有堆叠」：拖动右下角把「健身」拉高，「旅行规划」被压在下面不动；
要求「调整大小时其它卡片实时被挤出去」。

### 两个真根因
1. **`pointerInput(Unit)` 捕获的是首次组合的回调**（`ResizeGrip` + `cardBodyGestures`）。
   这两个手势块只跑一次，里面拿到的 `onResizeEnd/onResizeStart` 永远是第一帧那组闭包，
   而 `settle()` 里读的 `packed`（整块画布）也是那一刻的旧值——**松手整理一直在拿旧画布算**，
   算完等于「没有变化」于是 `changed.isEmpty()` 直接 return，一条都不落库 → 重叠永远留在屏幕上。
   修法：两处手势的回调全部套 `rememberUpdatedState`，`detach` 时取 `.value`。
   教训：**Compose 里只要 `pointerInput(Unit)`/`LaunchedEffect(Unit)` 里调回调，就必须 rememberUpdatedState**。
2. **尺寸连续变形 + 邻居按格子占位** 天生不可能对齐：卡片画 2.6 格宽、占位取 2 格时，多出的 0.6 格
   就是压住邻居的那部分。所以「实时让位」的前提是**画出来的大小 == 占的格子**。

### 改法
- `CardBoard`：删掉 `ALLOWED_SHAPES / CardShape 六档 / isAllowed / nearestShape / allowedShape / resizeToAllowed`，
  换成 `snapShape(cols, rows, maxCols, maxRows)`：**逐轴四舍五入**（横向只改列、纵向只改行）。
  旧的「六种预设里找最近二维点」会出现「往宽了拖反而变窄」，且 3×2 这类尺寸根本拖不出来。
  现在 1–4 格都能拖出来，`normalize` 负责夹取。
- `DayCardBoard`：
  - `resizeShape`（由 live px 算出）+ `resizeAnchor`（锚点占位）→ 每帧跑一次 `CardBoard.arrange`，
    结果放进 `pushed: Map<String, CardBox>`，**只用于渲染、不落库**；
  - 卡片按 `resizeShape` 绘制（`animateDpAsState` 90ms），尺寸与占位永远一致；
  - 邻居用 `rememberCardOffset` 做 150ms 补间滑出去，正在拖的那张逐帧直给；
  - `endResize` 直接提交 `snapShape` 的结果（不再二次吸附）→ 松手 = 眼前画面，零跳变；
  - 跨格时给一次 `TextHandleMove` 轻触感，让「吸附」有反馈；
  - `activeResizeBottomPx` 改用吸附后的行数，避免画布高度跟着手指呼吸。
- `autoPlaced` 的修复标记从 `fix-p{id}` 改成 `fix-p{id}@{x},{y}`：同一张卡一局里可能被压到多次，
  按 id 去重会让第二次起再也修不动。
- 测试：`CardBoardTest` 仍 28 条（删 5 条六档规格，加 3 条 `snapShape` + 2 条 `arrange`：
  「照截图局面放大后全盘无重叠」「缩回原尺寸能回原位」），总数 **702** 全绿。

## 20:24 v1.1.27 三个手感 bug：手柄难触发 / 放不了 / 卡片闪一下变小

用户报三条，前两条其实是同一个根因（逐张落库的中间态被当成真状态）。

### 1) 长按右下角有时拖不动

## 20:40 v1.1.28 让位不再连锁 + 手柄彻底修好

### 1) 点右下角拖不动了（v1.1.27 引入的回归）
上一版把手柄换成 `awaitEachGesture + drag()`：先 `down.consume()` 再 `drag(down.id)`。
`drag` 内部 `awaitDragOrCancellation` 要求 `change.isConsumed == false`，
而 `positionChange()` 在事件被消费过之后会**返回 0**——只要上游有谁碰过这个事件，
手柄就一个像素都推不动。表现就是"点了没反应"。
修法：不再用 `drag()`，自己循环 `awaitPointerEvent()`，
**用 `change.position - change.previousPosition` 算原始位移**，完全绕开 consumed 判断。
另外补了两条护栏，让两种手势互不误伤：
- `startMove` 在 `gesture == RESIZE` 时直接 return（缩放手势优先）；
- `cancelMove` / `cancelResize` 只在当前确实是该手势时才 `resetGesture()`，
  避免长按拖动那一路被 Cancel 时把正在进行的缩放一起清掉。

### 2)「没碰的卡也乱跳」= arrange 的连锁让位
`arrange` 里判断空位用的是 `placed`（**已经落位的那几张**），
还没处理到的卡不在里面 → 被挤走的卡可以"搬进别人家里"，
于是那张还没处理的卡再被挤走，连锁。
改成拿**整块板子**判断：`resolved` 先填满所有卡的当前占位（已处理用新位置、没处理用原位置），
每次 `fitsAt` / `resolveMove` 都对照它。
新增 `arrange_doesNotCascadeIntoUntouchedCards`，总数 **707**。

## 20:52 v1.1.29 换掉自研排版：改用 dashboard 网格的「向下让位」模型

用户截图仍有重叠，且要求「去 GitHub 找开源代码」。

### 调研结论（先查后写）
- Compose 生态里没有能用的现成方案：`sh.calvin.reorderable`、`MohamedRejeb/compose-dnd`、
  `ComposeDragAndDrop` 都是**列表/网格重排**（固定尺寸的格子换来换去），
  不支持「任意大小的卡 + 自由坐标 + 拖动 + 缩放 + 实时让位」。
  `compose-dnd` 有 Free-Form Placement，但只是自由落点吸附，不是多格卡片排版。
- 真正对口的实现都在 Web：**gridstack.js**、**react-grid-layout**（都是 MIT），
  以及 **Muuri**。它们的核心是 collision + push-down，代码量小、模型清晰，移植算法即可。

### 新模型（CardBoard.arrange 重写）
```
placed = [anchor]
按 (y, x) 顺序处理其余每张卡：
    y = 原 y
    while 与 placed 里任意一张重叠:
        y = 所有碰撞卡的下沿最大值      // 直接跳过必然还撞着的那段
    放到 (x, y)
```
性质（都被单测钉住）：
- **构造性无重叠**：落位前和已落位的全部卡比对，落位后不再移动；
- **只往下、列不变**：不会横向乱窜，也就不会互相顶来顶去；
- 处理顺序固定 → 同一局面结果唯一。
替换掉了原来"找最近的空位"（Manhattan 距离搜索），那个模型会让卡横向跳、还会连锁。

### 另外两道保险
- `CardBoard.hasOverlap` + 渲染前兜底：`effective` 只要还叠着就先 `arrange` 一遍再画 ——
  "屏幕上不出现两张压着的卡"优先于省一次计算。
- 拖动时画 `DropOutline` 落位虚框：手上浮着的卡 ≠ 占位，把占位画出来，消除"怎么又叠上了"的错觉。
- 老数据修复也改用同一套 `arrange`（锚点取第一张），不再有两套让位逻辑。

### 测试

  `arrange_onlyPushesDownAndKeepsColumns`；两条旧的"最近空位"断言改成"往下让"。

## 21:38 v1.1.30 「只挪一张卡，别的卡也动」的两个真凶

### 1) 上一版加的「渲染前兜底」是灾难
```kotlin
val effective = if (CardBoard.hasOverlap(raw) ) CardBoard.arrange(raw, raw.first()) else raw
```
只要 `effective` 里出现一次重叠（哪怕只有一帧、来自 pending 混合旧值），
这一行就会**以第一张卡为锚点重排整块板子**；更糟的是 `settle` 拿 `arranged != effective` 算差异，
于是这次重排会被**提交**。表现就是"我只动了一张卡，别的卡自己动了"。
**删除**。教训：兜底逻辑不能改动被提交的数据源，`effective` 必须是唯一真相。

### 2) settle 的差异基准是"当前布局"，不是"手势开始时的布局"
`changed = arranged.indices.filter { arranged[it] != effective[it] }` ——
只要手势期间 `effective` 有丝毫变化，差异里就会混进与本次拖动无关的卡，被一起写库。
新增 `gestureBase`：`startMove` / `startResize` 时把 `effective` 拍个快照，
整个手势的 `previewArrangement`、`pushed`、`settle` 全用它当基准。
于是"这次拖动到底动了谁"从数据流上就是确定的。

### 3) pack 也补上不重叠保证
历史数据可能两张卡在同一格（旧版本允许叠放），`pack` 原样返回 → 之后每次整理都在坏局面上算。
`pack` 末尾加一遍"后到的往下让"，并有单测 `pack_neverReturnsOverlappingCards`。
`needsPlace` 从 `x<0||y<0` 放宽到"位置和 pack 结果不一致就写回"，让修好的布局落库。
顺带删掉了原来的一次性 `legacyRepaired` 修复块（已被 pack + needsPlace 覆盖）。

### 测试
- 709 → **711**：`arrange_droppingIntoEmptySpaceMovesNobodyElse`、`pack_neverReturnsOverlappingCards`。
- 包 1.1.30（code 258）。

## v1.1.31 —— 缩放手柄「很难触发」根治：手势路由合一

**症状**：右下角拖动调整大小反复难触发（v1.1.27~30 三轮小修未愈）。

**根因**：ResizeGrip 是卡片右下角独立的 44dp composable，自带一套 pointerInput。三重不利叠加：
1. 热区只有 44dp，再被卡身 RoundedCornerShape(16~20dp) 的 `clip` 削掉角落——手指最自然落点（正角落）恰好命中不了；
2. 与卡身 `detectDragGesturesAfterLongPress` 是两套手势，靠「down.consume() 抢先」维系，时序稍偏就被 500ms 长按抢回去；
3. 小手柄 + 大图手势的命中调试本身脆弱。

**修法（结构性）**：删掉手柄自己的手势，把它降成纯视觉角标；`cardBodyGestures` 改成**唯一手势入口**，`awaitEachGesture` 里先看按下落点：
- 落在右下角 56dp 见方（角标所在）→ `down.consume()`，手指一动即 `startResize`，原始坐标差逐帧 `resizeBy`；
- 落在其它区域 → `awaitLongPressOrCancellation` 等 500ms 进移动拖动；长按后带 touch slop（手写循环里用 `viewConfiguration.touchSlop` 累计位移，超阈值才 `moveStart`），原地松手仍弹操作菜单。

**教训**：两个手势抢同一块区域时，正解通常不是「让其中一个更会抢」，而是**按落点在同一个手势里路由**，竞争从根上消失。命中区域用「整张卡的坐标」判断，比指望一个小 composable 的热区可靠得多。

测试 711 条全绿，构建通过。

## v1.1.33 —— MuMu 真机实测：抓到并修掉「松手落库 ≠ 屏幕预览」

**实测方式**：MuMu 12 实例 0（`127.0.0.1:16384`，Android 15，物理 1272x2261）。`adb install -r -t` 装 debug 包 → `monkey` 启动 → 点日期格 (923,700) 进日卡片画布。`uiautomator dump` 在这台机 segfault（只能拿到旧缓存），改用 `screencap` + `input motionevent DOWN/MOVE/UP` 注入手势（长按先 DOWN、sleep 0.75s、再逐步 MOVE），并用 `run-as com.focuslist.app cat databases/focus_list.db{,-wal,-shm}` 导出 SQLite 读 `plans.cardX/cardY/cardCols/cardRows` 作精确 oracle。列宽/行高 ≈312px，画布起点 (20,284)。

**抓到的真 bug**：拖 Stretch 压住 Run 时，中途截图预览是 Run 上移到 (2,1)，松手后落库却成了 (0,2)。临时 `Log.d` 显示 `endMove` 里 `previewAnchor=null`、`previewArrangement=null` → `settle` 走兜底 `CardBoard.arrange(baseline, anchor)`，而 `baseline` 是**旧组合那一帧**（Read 还是 1×2），于是算出完全不同的落点。
根因：`pointerInput` 的回调经 `rememberUpdatedState` 传递，但 Compose 可能跳过中间 `PlanBoardCard` 的重组合，回调仍指向旧组合创建的函数。`var x by remember { mutableStateOf() }` 的 State 委托跨组合共享、读到最新值；`effective` / `previewArrangement` / `previewAnchor` / `plans` 是普通 val，是旧帧死快照。新旧混用 → 手势用新状态、落库用旧布局。

**修法**：① `effectiveNow` / `zNow` 放进 State + `SideEffect` 每帧刷新；`onPlanLayout`/`onTripLayout` 走 `rememberUpdatedState`；`startMove`/`startResize` 从 `effectiveNow.value` 取基准。② `settle` 不再依赖组合里的 `previewArrangement`，直接用 `gestureBase`（State）重排——`arrange` 是纯函数，同一基准 + 同一锚点必然等于预览，且落库逐张写的中间态影响不到它。③ `CardBoard.arrange` 选空位时，同一行按 `|x - 原列|` 排序，被挤的卡优先补自己那列上方的洞，不再从最右列横跳到最左列。

**实测覆盖（全部通过）**：右下角一按即缩放并正确落库；长按拖到空白只动自己；拖到别人身上被挤的卡往上补洞；缩放放大时邻居实时让位；「预览 ↔ 落库」连做 3 轮（含中间插一次缩放制造旧组合）全部一致；拖到远处空白、拖回原位、缩回原尺寸均无连锁乱跳；轻点进统计、长按原地弹菜单、点右下角不误触详情；全程无重叠、无卡片变小/消失。

**教训**：Compose 里凡是会被 `pointerInput` 回调读取的东西，必须是 State，不能是组合局部 val；`rememberUpdatedState` 只在「它所在的那个 composable 真的重组合了」时才更新，中间层被跳过就失效。真机 + 数据库读坐标比看截图猜要可靠得多。

单测 713 条全绿（CardBoardTest 39 条，新增 `arrange_pushedCardPrefersItsOwnColumn`），构建通过。
